# Как участвовать в разработке MacroStress

MacroStress принимает сообщения об ошибках и предложения изменений через GitHub. Небольшое
исправление можно сразу оформить запросом на слияние — pull request. Новый драйвер, тип
актива или источник данных сначала обсудите в issue, то есть отдельной задаче репозитория:
обсуждение должно определить границы изменения до правки общего контракта.

## Подготовка окружения

Нужны Python 3.12 или новее и [uv](<https://docs.astral.sh/uv/>), инструмент установки
зависимостей и запуска Python. Из корня репозитория выполните:

```powershell
uv sync
uv run pytest -q -m "not slow"
uv run ruff check .
```

Команда `uv sync` создаёт виртуальное окружение и устанавливает пакет `mst` в редактируемом
режиме: изменения исходного кода доступны без повторной установки пакета. `pytest`
проверяет поведение, а `ruff` проверяет правила оформления и часть ошибок кода.

Быстрый набор исключает тесты с меткой `slow`. Полный набор добавляет длительные проверки
оценки байесовской векторной авторегрессии (BVAR), модели совместной динамики показателей:

```powershell
uv run pytest -q
```

Перед запросом на слияние нужны быстрые тесты и `ruff`; полный набор выбирайте, когда
изменение затрагивает оценку модели или длительные проверки. Быстрая проверка сокращает
время обратной связи, но не подтверждает поведение исключённых тестов. Автоматическая
проверка изменений задана в [CI](<.github/workflows/ci.yml>), а полный набор запускается по
расписанию и вручную через [Full test suite](<.github/workflows/slow.yml>).

## Где искать нужную часть

Вычислительный код находится в пакете `mst`; обзор контрактов и руководств — в
[документации](<docs/README.md>). Каталоги пакета разделены по ответственности:

| Задача изменения | Отправная точка |
|---|---|
| Загрузка источников и хранение временных рядов | [Данные](<src/mst/data/README.md>) |
| Работа с макромоделями и их общим интерфейсом | [Макромодели](<src/mst/macro/README.md>) и [каталог моделей](<src/mst/models/README.md>) |
| Показатели активов и модели их связи с макроэкономикой | [Драйверы](<src/mst/drivers/README.md>) |
| Поиск источников сценария | [Корпус](<corpus/README.md>) |
| Условия события и формат сценария | [Сценарий](<src/mst/scenario/README.md>) |
| Позиции, оценка и агрегирование результата | [Портфель](<src/mst/portfolio/README.md>) и [расчётный движок](<src/mst/engine/README.md>) |
| Расширение новыми типами объектов | [Плагины](<docs/howto/plugins.md>) и [SDK плагинов](<src/mst/plugin_sdk/README.md>) |
| Подключение к DeepSeek Harness | [Плагин приложения](<dsh/README.md>) |

Драйвер — именованный показатель, который нужен для оценки позиции; сателлитная модель
связывает такой показатель с макроэкономикой. Новый тип актива добавляется плагином,
поэтому его правила оценки не нужно встраивать в общий расчётный движок. SDK — набор
интерфейсов для такого расширения. Сервер Model Context Protocol (MCP), протокола вызова
инструментов, предоставляет расчёты агенту; интеграция с DeepSeek Harness использует
тот же сервер.

## Правила кода и тестов

Настройки `ruff`, длина строки 100 символов, зависимости и параметры тестов закреплены в
[pyproject.toml](<pyproject.toml>). Публичные функции получают аннотации типов, а структуры,
пересекающие границу пакета, описываются `dataclass` или моделями Pydantic. Новая зависимость
допустима, только если задачу не решают стандартная библиотека и уже установленные пакеты;
причину добавления объясните в запросе на слияние.

Тесты размещаются в соответствующей части [каталога тестов](<tests/README.md>) и не должны
обращаться к сети. Вместо ответов источников тест использует подготовленные примеры, а модель проверяет
на рядах, сгенерированных с известными параметрами. Сетевая доступность
поставщика данных не должна определять результат программного теста.

Документация и комментарии пишутся по-русски; код, имена инструментов и сообщения коммитов —
по-английски. Объясняйте изменение так, чтобы читатель мог проверить правило без истории
обсуждения.

## Подготовка запроса на слияние

Держите в коммите одну тему. Исправление ошибки, новая возможность и самостоятельная
правка документации оформляются раздельно, чтобы каждую часть можно было проверить или
отменить отдельно. Заголовок коммита пишется в повелительном наклонении; если причина
изменения не следует из правки, объясните причину в теле сообщения.

Перед отправкой выполните быстрые тесты и `ruff`, затем убедитесь, что автоматические
проверки GitHub завершились успешно. Изменение инструмента или контракта должно обновлять
соответствующую документацию и добавлять запись в `Unreleased` — раздел ещё не выпущенных
изменений [журнала версий](<CHANGELOG.md>).

## Выпуск версии

Порядок выпуска предназначен участнику с правами публикации и не заменяет проверку кода.
Версии пакета и плагина должны совпадать, а публикация запускается тегом версии.

1. Перенесите записи `Unreleased` в [журнале версий](<CHANGELOG.md>) под номер новой версии
   и укажите дату выпуска.
2. Обновите поле `version` в [описании Python-пакета](<pyproject.toml>) и
   [описании плагина](<dsh/package.json>).
3. Создайте коммит и тег вида `vX.Y.Z` и отправьте тег в репозиторий. Процесс
   [Publish](<.github/workflows/publish.yml>) собирает пакет и публикует его в PyPI через
   доверенного издателя, без токена в репозитории.
4. Создайте выпуск GitHub из тега, используя соответствующий раздел журнала версий как
   описание выпуска.

Имя проекта в PyPI — `macrostress`. Доверенный издатель настраивается для репозитория,
процесса `publish.yml` и окружения `pypi`; конфигурация процесса находится в
[описании публикации](<.github/workflows/publish.yml>).
