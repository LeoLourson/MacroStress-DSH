# Платформа: контракты расчёта

Общая схема системы — [../concept/formalization.md](../concept/formalization.md); ниже — контракты, которыми она
реализована.

MacroStress — модульный монолит без базы данных, веба и оркестратора. Состояние — файлы
одного каталога `workspace/`; долгие операции идут задачами. Ядро не знает ни типов
активов, ни конкретных моделей: оно даёт данные, версии моделей, сценарий, диспетчер
расчёта, агрегат и отчёт. Всё предметное — акция, облигация, кредит, недвижимость,
макромодель и сателлит величины — подключается пакетами-плагинами
([../howto/plugins.md](../howto/plugins.md)). Поток данных и каталог workspace описаны в
[../concept/architecture.md](../concept/architecture.md).

## 1. Слои

| Слой | Пакет | Что даёт |
|---|---|---|
| Данные | `mst.data` | Месячные ряды с датой публикации каждого значения; `as_of` не видит будущих пересмотров |
| Уровень 0 | `mst.macro` + плагин | Реестр переменных, панель на дату, версии; сама модель (BVAR `bvar.sv`, MS-VAR `msvar.markov` и любые другие) — плагин `MacroModel` |
| Уровни выше | `mst.drivers` + плагины | Объекты и величины, подготовка истории, бандл версии — своя сателлитная модель на величину (`SatelliteModel`), проверка вне выборки в части версии |
| Сценарий | `mst.scenario` | $s=(N,m,O,D,\mathcal C)$: нарратив, версии, воздействия на любом уровне, причины, условия; `build` даёт пути, `overlay` — наклон, `reverse` — обратную задачу |
| SDK моделей | `mst.model_sdk` | План сценария, воздействия, контексты оценки, три шага модели, условная механика |
| SDK позиций | `mst.plugin_sdk` | `Paths`, требования, подготовленные входы, результат, версия SDK |
| Версии | `mst.models` | `estimate-macro`, `estimate-satellites` (назначение величин моделям), `diagnose-satellites` (что несёт сохранённый бандл: ро, эластичности, тяга к равновесию), список и описание |
| Ядро расчёта | `mst.engine` | Каталог моделей, подготовка входов, расчёт позиции, проверка результата |
| Плагины | `mst.plugins.<id>` | Модели позиций, макро- и сателлитные; реестр собран из пакетов, entry points и `MST_PLUGINS_PATH` |
| Качество | `mst.metrics` | Ячейки $(e,t,q)$, CRPS, калибровка, допуск, эталоны, эпизодный бэктест |
| Портфель | `mst.portfolio` | Портфель, проверка против версий, стоимость и отчёт |
| Расчёт | `mst.runs` | Пути, условный прогноз показателей и результаты в `runs/<id>/`; тот же сид — те же числа |
| Сервер | `mst.mcp`, `mst.jobs`, `mst.store` | MCP-инструменты, задачи, каталог workspace |

## 2. Workspace и версии

Версия модели — неизменяемый каталог `<sha256>/` с `meta.json` и `arrays.npz`. Хеш покрывает
метаданные и массивы; изменённый файл при загрузке отклоняется. Версия называет модель,
которая её оценила (`meta["model"]`), и читается обратно только этой моделью; обязательные
ключи (даты, переменные, шоки, панель) проверяет платформа, остальное — формат самой
модели. Сателлитная версия — бандл: часть на каждую величину, своя модель на часть,
корреляция остатков всех драйверов с историей. Сателлиты оцениваются на панели конкретной
макроверсии и хранят её хеш. Сценарий называет обе версии; расчёт фиксирует их в
`meta.json`, поэтому смена версии не смешивает числа одного расчёта.

Ряды хранят каждое значение с датой публикации. `as_of(day)` возвращает то, что было
известно в тот день; при первой загрузке дата пересмотра оценивается и помечается
`approximate = 1`. Оценка модели, сценарий и расчёт читают только данные не позже своей
даты.

Ответы опроса моделей лежат в `workspace/elicitation/<дата>/<ключ>.json`: модель, чья
оценка читает ответы, а не только ряды, объявляет их ключи методом `input_keys` SDK 3.1,
инструмент `elicit` выдаёт один малый вопрос через `next`, сохраняет часть через `answer`
и возвращает следующий вопрос. Незавершённые ответы хранятся отдельно в `elicitation/.steps/`
и не участвуют в оценке. Полный ответ собирается без подстановки чисел и проходит прежнюю
проверку модели; полноразмерные `question/write` доступны в `model(kind="inputs")`;
человек ответы не утверждает — их проверяют форма и сама модель. Оценке такая модель
получает в контексте папку ответов (`inputs`), свою папку точек сохранения
(`checkpoints`, убирается после записи версии) и callable видимости фрагментов корпуса
модели (`fragment`). У моделей свой корпус — `workspace/corpus-model` с отдельными
манифестом и индексом (вид источника `market` — рыночные ожидания); инструмент `corpus`
выбирает его параметром `corpus="model"`, и Agent видит только материалы, опубликованные
до даты расчёта.

Цена сценария читает закон условий у модели: `constraint_law` даёт строки-смеси гауссовых
законов, а когда никакая смесь не несёт закон (причины называют шоки с нелинейными
входами), модель может вернуть собственные вероятности ящика методом
`log_box_probability` — цена и её ошибка тогда среднее и разброс `-log P(S|R)` по
значениям `R`, односторонняя цена берёт медианы из свободной симуляции с теми же
причинами.

## 3. Позиция и пути

`Position` — что это, сколько стоит и по какому объекту сопоставляется:

| Поле | Смысл |
|---|---|
| `id`, `name` | Идентификатор и подпись позиции |
| `type` | Тип актива; по нему реестр выбирает модель |
| `currency` | Валюта позиции; базовая валюта портфеля — рубль |
| `notional` | Текущая стоимость в миллионах валюты |
| `codes` | `secid`, `isin`, `inn`, `okved`, `okato` — коды объекта для сопоставления с драйвером |
| `terms` | Собственные входы модели по её схеме (`duration`, `lgd`, `market`) |

`Paths` — один объект на расчёт: `draws` (R), `horizon` (H), `months` (t = 0 … H),
`variables`, `seed`; `macro(name)` и `driver(id_)` возвращают массивы `(R, H + 1)` в
исходных единицах, `flags(id_)` — пометки драйвера (`parameters_from_above`,
`approximate_data`, `impact`). Месяц
`t = 0` — месяц расчёта, последний месяц истории.

## 4. Модель

Модель — `mst.plugin_sdk.CalculationModel`:

```
requirements(position, options) -> DataRequirements
validate(prepared)              -> list[Diagnostic]
calculate(prepared, context)    -> CalculationResult
```

- `DataRequirements` перечисляет драйверы (`DriverRequirement`: величина, объект или коды
  позиции) и макропеременные. Платформа разрешает драйвер в каталоге сателлитной версии;
  неразрешённый обязательный драйвер оставляет позицию без расчёта с её именем.
- `PreparedInputs` — позиция, модель, дата, горизонт, база, стоимость на `t = 0`,
  разрешённые драйверы и неразрешённые с причиной, исходные требования.
- `CalculationContext` — дата, горизонт, сид, база и `paths`.
- `CalculationResult` — статус (`ok`/`needs_review`/`invalid`), изменение стоимости по
  розыгрышам, метрики (значение и/или P5/P50/P95, у потерь ES95), пометки и диагностика.

Модель чистая: она не читает workspace, сеть и не разыгрывает случайные числа. Числа
считаются на общих реализациях сценария, поэтому две позиции одного объекта видят одни и
те же пути, а порядок позиций не меняет результат.

## 5. Диспетчер и статусы

`engine.prepare` проверяет `terms` по схеме модели, спрашивает `requirements`, сверяет
макропеременные с путями, разрешает драйверы и отдаёт входы в `validate`. Ошибка на любом
шаге — `invalid` с причиной; позиция остаётся в расчёте и в покрытии отчёта.

`engine.calculate` вызывает `calculate` и сверяет выход с объявлением: идентичность
позиции, модели и версии, статус, длину `value_change`, объявленные и обязательные метрики.
Нарушение — `invalid`; исключение модели — `invalid` с кодом `model_error:<Тип>`. Одна
сломанная модель не останавливает остальные позиции.

`engine.run` считает список позиций на одних путях и возвращает `Batch`: результаты в
порядке позиций и худший статус. `invalid` не входит в арифметику портфеля; `needs_review`
входит, и отчёт это раскрывает.

## 6. Реестр плагинов

`mst.plugins.discover` импортирует каждый пакет `mst.plugins.<id>` и читает его
`plugin = Plugin(...)`. `mst.plugins.build` проверяет объявления вместе и строит `Registry`:
плагины, модели по id, владелец каждой модели. Проверки:

- `plugin_id` — lower_snake_case, не повторяется;
- версии плагина и модели — `x.y.z`, диапазон SDK совместим с `SDK_VERSION`;
- id модели и метрики начинается с `<plugin_id>.`, не повторяется; тип актива обслуживает
  ровно одна модель;
- `required_metrics` входят в `metrics`; схема `terms` даёт JSON Schema;
- у плагина с моделями позиций есть демо-кейс, его тип обслуживает модель, обязательные
  драйверы отображены в драйверы, которые есть в путях; плагину только с макро- или
  сателлитной моделью демо-кейс не нужен.

Проблема любого плагина блокирует старт с перечнем всех проблем и имён плагинов. Каталог
`mst.engine.model_catalog` строится из реестра; других путей к моделям у ядра нет.

## 7. Сценарий, расчёт, отчёт

Сценарий — файл `scenarios/<id>.json`: нарратив, причины, условия на пути, средние и
вероятности, воздействия на макропеременные или драйверы, ссылки на фрагменты корпуса, горизонт,
обе версии и тот, кто его утвердил. Воздействие — путь значений от месяца `start`:
`values[k]` прибавляется в месяце `start + k`, пропуск внутри пути — записанный нуль,
постоянный сдвиг — повторённое значение; собственной динамики у воздействия нет, поэтому
последействия — ненулевые значения после события. Воздействие на макропеременную, уровень 0,
— аддитивный сдвиг после $G^0$, внутри уровня 0 не распространяющийся: остальные
макропеременные не получают реакции, которую дал бы шок $D$. Условия относятся к итоговому
пути $F_O(\omega)$, поэтому макромодель решает их против сдвинутой траектории (обе границы
уменьшаются на воздействие этого месяца), а воздействие прибавляется к путям после
розыгрыша. `mst.scenario.build` строит условный прогноз макромодели при условиях, наклоняет
причины под условия на средние, возвращает переменные в исходные единицы, считает пути
драйверов на тех же розыгрышах, цену $\mathrm{dist}(s)$ и её одностороннюю пару
$\mathrm{dist}^+(s)$. Условие, которого не достигают причины, неизвестная переменная,
воздействие на необслуженный драйвер, путь воздействия за горизонтом и чужая версия
сателлитов — отказ с именем причины.

`mst.runs` пишет в `runs/<id>/` запрос, метаданные, пути, результаты и отчёт. Расчёт —
функция от сценария, версий, числа розыгрышей и сида: тот же запрос даёт те же числа
побитно. Отчёт портфеля складывает потери **внутри розыгрыша** и только потом берёт P5,
P50, P95 и ES95 — на конце горизонта, по каждому месяцу и по всему пути
(`losses_by_month`, месячный массив — в `path_losses.npz`); сумма P95 позиций не выдаётся
за P95 портфеля. Отчёт сравнивает те же потери с пустым сценарием $s_0$ на общих случайных
числах (`comparison`: сдвиг центра закона отдельно от изменения ширины, каждое с
интервалом) и допускает расчёт, лишь пока меньше пяти процентов ячеек месяца и величины
нарушают каждое условие допуска, — иначе статус `not_admitted`, нарушенные условия и
величины названы, числа остаются для диагностики. Долю путей, которым условия сценария нужны
через движущий шок больше шести стандартных отклонений (`DRIVING_LIMIT`), отчёт показывает
флагом `driving_shock_above_limit`, если она достигает того же порога: отклики на такой шок
экстраполированы. В отказ она не ведёт, потому что маловероятность события измеряет цена
сценария, а решение ЦБ сценарий может задать сам. Исключённая позиция названа с причиной,
покрытие — доля стоимости, которую числа покрывают; `dist` — цена сценария с её
составляющими и пометкой `estimated`, без условий её нет.

## 8. MCP и DSH

`mst.mcp` — единственный сервер: инструмент разбирает аргументы и вызывает одну функцию
пакета или запускает задачу. Долгие операции (оценка, загрузка, расчёт) идут дочерним
процессом `python -m mst.<пакет>` на своём ресурсе; вторая задача на том же ресурсе
получает отказ. Справочник — [tools.md](tools.md).

`dsh/` — плагин DSH: он запускает этот сервер, регистрирует скиллы и добавляет в системный
промпт раздел из `workspace.json`. Скиллы объясняют агенту, как собрать сценарий из
корпуса, прочитать отчёт и что значит «сателлит отвергнут».

## 9. Чего в платформе нет

- базы данных, HTTP API и веба: состояние — файлы workspace;
- LangGraph и агентов расчёта: сценарий собирает внешний агент DSH через MCP;
- снимков данных и срезов портфеля: позицию задаёт номинал, а модель читает пути;
- правил допуска `needs_review` и снэпшотных цен: отчёт показывает статус, но не решает
  за риск-менеджера.
