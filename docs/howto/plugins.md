# Плагины: модели позиций, макро- и сателлитные

Платформа расширяется плагинами, и подключается всё — не только позиции. Плагин — пакет с
объявлением `plugin = Plugin(...)`, своими моделями, тестами и README; вид задаётся тем,
что объявлено: `models` — модели позиций, `macro` — макромодели уровня 0, `satellites` —
сателлитные модели величин. Референсные модели платформы — BVAR (`src/mst/plugins/bvar`)
и иерархический сателлит (`src/mst/plugins/hier`) — обычные плагины: они разрабатываются
и подключаются как любые другие, ядро их не знает.

Ядро при этом не меняется: если для новой модели пришлось править `mst.engine`,
`mst.scenario`, `mst.runs` или `mst.metrics`, значит, в SDK не хватает точки расширения —
это отдельное изменение SDK, а не часть плагина.

Контракты, на которые опирается плагин, описаны в [../reference/platform.md](../reference/platform.md).

## 1. Быстрый старт

```powershell
python -m mst.plugin new gold --label "Золото"                     # модель позиции
python -m mst.plugin new walk --kind macro --label "Блуждание"     # макромодель
python -m mst.plugin new link --kind satellite --quantity share_price
python -m mst.plugin check gold                     # контракт; для позиций ещё демо-расчёт
python -m mst.plugin demo-run gold                  # P5/P50/P95 на демо-путях
python -m mst.plugin check                          # все установленные плагины
```

`new` создаёт пакет, который **сразу проходит** `check`:

```
src/mst/plugins/<id>/
  __init__.py        экспорт MODEL и plugin
  plugin.py          plugin = Plugin(...)
  model.py           модель: свои шаги (см. вид ниже)
  tests/             тесты пакета
  README.md          что даёт плагин и что в нём менять
```

Пакет в `src/mst/plugins/` платформа подключает при следующем запуске. Пакет вне
репозитория создаётся с `--dest DIR` (в `DIR/<id>`) и проверяется там же:
`python -m mst.plugin check --path DIR/<id>`; `demo-run --path DIR/<id>` считает его
демо-кейс без установки. Модель, разрабатываемая отдельным пакетом-распределением,
подключается entry point'ом группы `mst.plugins`; каталоги с пакетами — переменной
окружения `MST_PLUGINS_PATH` (через `os.pathsep`): три способа, один реестр.

Пакет, подключённый по пути (`--path`, `MST_PLUGINS_PATH`), импортируется под синтетическим
именем `mst_plugin_<папка>`, поэтому внутри пакета нужны относительные импорты
(`from .model import MODEL`). Абсолютный `import <папка>.model` работает только у пакета,
установленного распределением (entry point) или лежащего в пространстве имён
`mst.plugins.<id>`; по пути он падает с `ModuleNotFoundError`. Путь в
`MST_PLUGINS_PATH`, который не является каталогом, — ошибка старта с его именем, а не
молчаливое «плагин не установлен».

## 1a. Модельные плагины: макро и сателлиты

Макромодель и сателлит говорят контрактами `mst.model_sdk` и только их:

- **Макромодель** (`macro=...`) — уровень 0: `estimate(контекст) → метаданные и массивы
  версии`, `load(мета, массивы) → модель версии`, `simulate(модель, план, draws, seed) →
  пути` и опционально `severity`. План (`ScenarioPlan`) — горизонт, ограничения $C$ и
  движущие шоки $D$; шоки — множество $J$ самой модели, сценарий сверяется с версией.
  Оценка: `python -m mst.models estimate-macro <model_id> --as-of ...`.
- **Сателлит** (`satellites=...`) — уровни выше: те же три шага, но `estimate` возвращает
  часть на каждую назначенную величину (месяцы, дерево объектов, наблюдения готовит
  платформа — `mst.drivers.history`), а `simulate` получает макросимуляцию, свои драйверы,
  воздействия $O$, свой поток случайных чисел и, если в бандле две и более модели, готовые
  `shocks` (см. ниже). Корреляция остатков — параметр, бандл передаёт свой срез. Оценка:
  `python -m mst.models estimate-satellites --macro <хеш>`;
  величину назначает декларация модели, а если величину заявили несколько — явное
  `--model ВЕЛИЧИНА=МОДЕЛЬ` (двусмысленность без имени — ошибка, не выбор); явное
  назначение может отдать модели и величину, которую она не заявляла.

Версия model SDK 1.1.0 добавляет в `simulate` сателлита необязательный `shocks`; контракт
обратно совместим по смыслу: при одной модели платформа зовёт `simulate` без `shocks`
(значение `None`), и модель разыгрывает свои остатки сама, как раньше. В бандле из двух и
более моделей платформа разыгрывает совместные шоки сама: на повторение $r$ — поток
`default_rng([seed, 0, r])`, `z ~ N(0, I)` по всем коррелируемым драйверам запроса, шоки
`z @ chol(Σ).T` по полной матрице корреляции версии (её приводит к положительно
определённой `assemble`). Каждая модель получает свой срез `(R, шаги, k)`: стандартизованные
остатки только её драйверов с историей, в порядке её аргумента `drivers`; драйверы
`parameters_from_above` остаются на независимом шуме модели. Строк платформа даёт
`horizon + max(len(part.months)) - 1` — столько нужно самой «долгой» модели, если её
последний наблюдённый месяц нулевой; модель читает первые нужные ей строки. Модель обязана
использовать эти столбцы: иначе кросс-модельная корреляция до совместных путей не доходит.

Версия несёт `meta["model"]` — id модели, которая её оценила; читает версию обратно только
этот плагин, поэтому формат мета и массивов (кроме обязательных ключей контракта) — дело
модели. Обязательные ключи: у макроверсии — `as_of`, `ids`, `months`, `shocks` и панель
(`panel_y`, `panel_approximate`); у части величины — `months`, `nodes`, `driver`, `rows`
(число месяцев, по которым оценён каждый узел) и `checks`. Ключ `model` у части платформа
пишет сама: часть, называющая другую модель, отклоняется — провенанс версии не подделать.

Эта версия SDK поддерживает $L = 1$: `simulate` сателлита получает только макросимуляцию
уровня 0. Модель уровня 2 строится, если сама готовит входы уровня 1; отдельного входа
уровней выше в контракте пока нет.

## 2. Объявление

```python
from mst.plugin_sdk import DemoCase, FixedPaths, Plugin, Position

plugin = Plugin(
    plugin_id="gold",
    version="0.1.0",
    sdk=">=1.0,<2.0",
    label="Золото",
    description="Позиция в золоте на путях его цены.",
    models=(MODEL,),
    demo=(DemoCase(...),),
)
```

| Поле | Что значит |
|---|---|
| `plugin_id` | Имя пакета и пространство идентификаторов: `gold.paths.v1` |
| `version` | Версия плагина `x.y.z`; проверяется `check` и попадает в реестр, прогон пишет версию модели каждой позиции |
| `sdk` | Диапазон версий SDK; несовместимый плагин блокирует старт с его именем |
| `label`, `description` | Как плагин называется и что даёт |
| `models` | Модели `CalculationModel`; их id начинаются с `<plugin_id>.` |
| `demo` | Демо-кейсы, на которых `check` и `demo-run` считают позицию |

Идентификатор модели и идентификатор метрики — `<plugin_id>.<имя>`. Тип актива глобален и
не может обслуживаться двумя моделями. Эти правила проверяет реестр при старте.

## 3. Модель

Модель — наследник `mst.plugin_sdk.CalculationModel` из трёх шагов:

```python
class GoldModel(CalculationModel):
    model_id = "gold.paths.v1"
    version = "0.1.0"
    label = "Золото на путях цены"
    instrument_types = ("gold_position",)
    terms_schema = Terms
    metrics = ("gold.value_current", "gold.pnl", "gold.loss")
    required_metrics = metrics

    def requirements(self, position, options):
        """Что нужно из путей: драйверы и макропеременные. Пути ещё не прочитаны."""

    def validate(self, prepared):
        """Суждение о подготовленных входах; error останавливает позицию."""

    def calculate(self, prepared, context):
        """CalculationResult на общих путях прогона; только чистые вычисления."""
```

- **`requirements`** возвращает `DataRequirements`: `DriverRequirement` (величина и, если
  нужно, объект или коды позиции) и имена макропеременных. Платформа находит драйвер в
  каталоге сателлитной версии; драйвер, которого нет, оставляет позицию без расчёта и
  называет величину.
- **`validate`** возвращает `Diagnostic`-и. `error` превращает позицию в `invalid` с
  причиной; она остаётся в прогоне и в покрытии отчёта.
- **`calculate`** читает только `prepared` (разрешённые драйверы, стоимость на `t = 0`,
  `terms`) и `context` (пути, дата, горизонт, сид, базовая валюта). Модель не читает файлы,
  сеть, workspace и не разыгрывает случайные числа. Результат собирается `envelope`;
  обязательные метрики должны быть в результате, длина `value_change` — числу розыгрышей.

Схема `terms` — pydantic-модель с `extra="forbid"`. Её поля — входы аналитика (дюрация,
LGD, рынок недвижимости), и у них нет молчаливых умолчаний: отсутствующее обязательное
поле — отказ с именем поля.

## 4. Демо-кейс

```python
DEMO = FixedPaths(
    drivers={"gold_price:demo": np.array([[100.0, 102.0, 104.0], [100.0, 98.0, 96.0]])},
    start=date(2026, 9, 1),
)

DemoCase(
    name="demo",
    position=Position(id="demo", type="gold_position", notional=100.0),
    paths=DEMO,
    drivers={"gold_price": "gold_price:demo"},
)
```

`drivers` — карта «величина требования → id драйвера в путях». `FixedPaths` — обычный
`Paths`: у него есть `draws`, `horizon`, `months`, `variables`, `macro`, `driver`, `flags`.
Демо-кейс самодостаточен: ни workspace, ни оценённых моделей, ни сети он не требует.

`check` считает каждый кейс через диспетчер платформы дважды: повтор должен дать те же
числа; позиция с `completes=True` должна рассчитаться, обязательные метрики — быть на месте.
`demo-run` печатает P5/P50/P95, ES95 для потерь и пометки результата.

## 5. Проверка и приёмка

`python -m mst.plugin check` проверяет:

- идентификатор плагина, версии плагина и моделей, диапазон SDK (`sdk` для позиций,
  `model_sdk` для макро- и сателлитных моделей), непустой `label` и хотя бы одна модель в
  `models`, `macro` или `satellites`;
- имена моделей и их принадлежность пространству плагина, уникальность типов актива;
- `metrics`: id вида `<plugin_id>.<имя>`, без повторов, `required_metrics` входят в
  `metrics`;
- схему `terms`: у неё есть JSON Schema;
- демо-кейс: его тип обслуживает модель, все обязательные драйверы отображены в драйвер,
  который есть в путях, макропеременные есть в путях;
- расчёт демо-кейса через `engine.run`: статус, обязательные метрики, детерминизм.

Плагин с моделями позиций без демо-кейса не проходит проверку: без него `demo-run` нечем
проверить. Модельному плагину (только `macro` или `satellites`) демо-кейс не нужен — его
проверяют контракт и сервисные тесты. Контракт шоков сателлита проверяется помощником
`mst.model_sdk.testing.check_shocks`: он зовёт `simulate` с `shocks` и без них на одном сиде
и сообщает находку, если пути совпали (модель проигнорировала шоки), если модель не
принимает аргумент или меняет форму путей. Тесты самого плагина лежат в
`src/mst/plugins/<id>/tests/` и запускаются после установки пакета:

```powershell
pytest src/mst/plugins/gold/tests
```

Общая проверка установленных плагинов — `tests/plugins/test_conformance.py`. Отдельно
`tests/plugins/test_boundary.py` падает, если ядро начнёт импортировать конкретный тип
актива или называть его идентификатор.

## 6. Границы

Плагин импортирует контракты и помощники ядра, а не оркестрацию:

- можно: `mst.plugin_sdk`, `mst.model_sdk`, `mst.contracts`, `mst.macro.panel`,
  `mst.macro.registry`, `mst.drivers.history`, `mst.drivers.registry` и собственный пакет;
  BVAR дополнительно читает контракт сценария (`mst.scenario.contracts`) в адаптере
  `to_scenario`, потому что инструмент сценария передаёт модели этот контракт;
- нельзя: `mst.engine`, `mst.scenario.build`, `mst.runs`, `mst.portfolio`, `mst.metrics`,
  `mst.models`, `mst.plugins` (реестр и другие пакеты плагинов) и модели других плагинов.

Ядро не называет ни одного конкретного типа актива: `mst.engine` спрашивает реестр, а
реестр собирается из пакетов `mst.plugins.<id>`.

Если модели не хватает возможности SDK (функции путей, поля результата, пометки), её
добавляют в SDK отдельным изменением ядра и повышают минорную версию SDK. Плагин,
которому нужна новая возможность, объявляет новый диапазон `sdk`.
