# ADR 0002: `jobs wait` держит вызов на сервере вместо опроса клиентом

Дата: 2026-11-03
Статус: принято

## Контекст

MCP-сервер не может сам «толкнуть» клиента: инициатива всегда на стороне клиента.
Инструмент, запускающий долгую задачу, сразу возвращает её id, и агенту, ждущему оценку на
несколько минут, оставалось гонять цикл `jobs(action="status")` и `jobs(action="log")` —
один раунд-трип на шаг, каждый с полной историей промпта, — или упереться в лимит шагов
рантайма раньше, чем задача кончится.

## Решение

У инструмента `jobs` появилось действие `wait`: сервер держит вызов до конца задачи или
истечения `timeout_sec` (30 по умолчанию, максимум 120) и возвращает запись, которую
возвращает `status`; `running` говорит вызывающему, ждать ли ещё. Цикл спит между дешёвыми
чтениями файлов, поэтому event loop продолжает отвечать на другие вызовы, пока один клиент
ждёт. Быстрая задача теперь стоит один вызов, длинная — по вызову на таймаут.

Параметр `wait_sec` на каждом запускающем действии рассматривался и отвергнут: он разрос бы
контракты всех инструментов флагом, меняющим возвращаемое значение, тогда как `wait` после
`start` даёт то же число раунд-трипов для быстрых задач и сохраняет фиксированную форму
ответа каждого инструмента.

## Последствия

Поток агента для долгой задачи — `start`, затем `wait` (ещё раз, пока `running` истинно),
с `log` для вывода. Инструкции сервера, гид `run-report`, справочник инструментов и
документ первого сеанса учат `wait`. Клиент с коротким таймаутом запроса увидит возврат по
своему таймауту, как и раньше; умолчание 30 с укладывается в типовые клиентские таймауты,
а потолок 120 с не даёт забытому вызову вечно держать воркер.
