# ADR 0002. Ожидание задачи на стороне сервера

После запуска долгой операции клиент MacroStress ждёт через `jobs(action="wait", id=...)`, а не запрашивает состояние в частом цикле. Сервер удерживает вызов до завершения задачи или таймаута и возвращает запись состояния. Такой порядок уменьшает число обращений агента и сохраняет отдельный идентификатор задачи для чтения вывода и отмены.

Дата решения: 2 ноября 2026 года. Статус: принято. ADR означает запись архитектурного решения; действующие параметры перечислены в [справочнике инструментов](<../reference/tools.md>).

## Почему ожидание отделено от запуска

Оценка модели и расчёт могут продолжаться дольше одного клиентского запроса. Запускающий инструмент поэтому сразу возвращает идентификатор задачи, а дочерний процесс работает независимо от завершения вызова. Без действия `wait` агенту приходилось бы многократно вызывать `status`, расходуя запросы и шаги своего исполнения, хотя состояние ещё не изменилось.

Сервер не требует от клиента поддерживать постоянное уведомление о завершении. Вместо такого механизма используется ограниченное по времени ожидание, совместимое с обычным вызовом инструмента. Вывод процесса остаётся доступен отдельно через `jobs(action="log", id=...)`.

## Принятый протокол

Параметр `timeout_sec` измеряет время ожидания в секундах: по умолчанию 30, разрешённый диапазон от 0 до 120. Ответ имеет форму `status`, включая `running` и `exit_code`. Если `running=true`, клиент может вызвать `wait` снова с тем же идентификатором. Значение `running=false` сообщает, что процесс завершился; успешность проверяют по коду выхода и результату операции.

Ожидание реализовано асинхронной функцией в [сервере MCP](<../../src/mst/mcp.py>): между чтениями состояния она передаёт управление циклу обработки запросов. Интервал чтения равен 0,2 секунды. Запись, проверка процесса и код выхода принадлежат [модулю задач](<../../src/mst/jobs.py>), поэтому `wait` не вводит вторую модель состояния.

```text
Запуск → идентификатор задачи → wait
                              ├─ running=true  → снова wait
                              └─ running=false → проверить exit_code и результат
```

Таймаут ожидания завершает только ожидающий вызов. Операция продолжает работать, пока не завершится сама или клиент явно не вызовет `cancel`.

## Рассмотренная альтернатива

Параметр ожидания на каждом запускающем действии смешал бы запуск и чтение состояния. Пришлось бы расширять схемы `series`, `corpus`, `model` и `run`, а возвращаемая форма зависела бы от того, успела ли задача закончиться. Отдельный `wait` требует дополнительного вызова после запуска, зато сохраняет одинаковый ответ запуска для быстрых и долгих задач.

Частый клиентский опрос остаётся технически возможным для клиента, которому нужен собственный интерфейс прогресса. Для агента принят `wait`, поскольку промежуточное чтение без новых данных не даёт нового основания для решения.

## Ограничения

Клиентский таймаут может быть короче `timeout_sec`; тогда клиент получит собственную ошибку ожидания, но задача продолжится. Предел 120 секунд ограничивает длительность одного удерживаемого вызова, а не длительность всей оценки. Значение по умолчанию 30 секунд снижает риск конфликта с короткими таймаутами клиентов.

Асинхронное ожидание не устраняет блокирующую работу других обработчиков в том же процессе. В проверке, записанной 2 ноября 2026 года, первый импорт каталога моделей при загруженном процессоре задержал ответ больше чем на 190 секунд; без такого вызова чтение состояния во время ожидания занимало около 0,1 секунды. Исторические замеры объясняют границу решения, но не задают нормативное время ответа для любого компьютера.
