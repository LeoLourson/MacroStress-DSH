# ADR 0005: Состояние остаётся в файлах, без SQLite и Arrow

Дата: 2026-11-02
Статус: принято

## Контекст

Внешнее замечание объявило хранение на файлах дефектом и предложило три миграции: реестр
задач, метаданные версий и каталоги перенести в SQLite в режиме WAL (`workspace/state.db`),
ряды в Parquet или DuckDB, пути расчёта в Arrow IPC с чтением через `mmap`. Доводы: гонки при
записи `workspace.json`, `PermissionError` на Windows, медленный срез `as_of`, сериализация
путей в JSON или CSV.

Мы проверили каждый довод по коду и на рабочем workspace:

- Версия модели — папка с именем sha256 от `meta.json` и `arrays.npz`. Черновик готовится
  рядом и переименовывается, когда записан целиком, поэтому оборванная оценка не оставляет
  версии. Готовая версия не меняется, и транзакции ей не нужны.
- Плоский JSON пишется через черновик и атомарную замену, читатель видит старый или новый
  файл целиком.
- Два задания не пишут в один ресурс: блокировку создаёт `O_CREAT | O_EXCL`, а блокировка
  завершившегося процесса считается устаревшей и перехватывается.
- `workspace.json` — снимок из последних версий и счётчиков, 473 байта на workspace с 33
  версиями и 24 расчётами. История в него не попадает, и размер от неё не растёт.
- `PermissionError` на Windows настоящий: читатель блокирует замену файла. Он лечится
  повторами замены (ADR 0004), база для этого не нужна.
- Пути лежат в `paths.npz`, JSON и CSV для них не используются. Самый большой файл, 48,6 МБ с
  массивами $(2048, 13, 23)$ и $(2048, 13, 205)$, загружается за 0,17 с.
- Срез `as_of` по всем 610 рядам (1,8 МБ CSV) занял 15,8 с при процессоре, загруженном на 100 %
  другими расчётами. Это 26 мс на ряд. Панель собирается один раз перед оценкой, которая идёт
  минуты.

## Решение

Файловое хранилище остаётся: JSON для состояния, CSV для рядов, content-addressed папки с `npz`
для версий, файлы блокировок для заданий. Для однопользовательского локального инструмента
миграция стала бы перестройкой ради перестройки: она не закрывает ни одного наблюдаемого
отказа, добавляет зависимость `pyarrow` и требует переноса данных.

Решение пересматривается, если выполнится хотя бы одно условие:

- один workspace одновременно используют несколько людей или в один ресурс нужно писать
  параллельно;
- workspace лежит на сетевом диске, где атомарность переименования и `O_EXCL` не гарантированы;
- массивы путей перестают помещаться в память;
- сборка среза `as_of` становится заметной долей времени расчёта.

## Последствия

Состояние читается и проверяется обычными инструментами, а хеши существующих версий не
меняются. Цена — отсутствие транзакций на несколько файлов и запросов по каталогу. Сбой между
двумя записями оставляет следы, которые разбирает код: устаревшую блокировку перехватывает
следующее задание, незавершённые записи задач закрывает `jobs(action="state")`. Поиск по версиям
и расчётам остаётся перебором папок.
